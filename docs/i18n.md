# Langues de l'interface

**Une seule option, un seul fichier par langue.**

```js
hugerte.init({ selector: '#contenu', language: 'nl' });
```

L'éditeur va chercher `langs/nl.js` tout seul, et ce fichier traduit **tout** : les menus et les
barres du cœur comme les formulaires des plugins ONLC. Il n'y a aucun script à inclure.

| Fichier | Ce qu'il contient | Chargement |
|---|---|---|
| `langs/<code>.js` | l'interface du **cœur et du thème** **plus** les intitulés des **plugins ONLC** | automatique, par `language:` |
| `langs/onlc/<code>.js` | les intitulés des plugins ONLC **seuls** | à inclure à la main — voir « Avec les paquets d'origine » |

## Comment un paquet est fabriqué

Deux générateurs, dans cet ordre :

```sh
# 1. Les chaînes du cœur, reprises de TinyMCE 6
node modules/hugerte/tools/i18n/build-langs.js

# 2. Les chaînes des plugins ONLC, ajoutées aux mêmes fichiers
node modules/hugerte/tools/openmoji/build-i18n.js
```

Le premier écrit `langs/<code>.js` à partir des traductions de TinyMCE 6 (licence MIT,
© Tiny Technologies Inc. et les contributeurs) ; 80 paquets sont livrés. Le second **ajoute** à
chacun les chaînes ONLC de la même langue, entre deux bornes :

```js
/* — ONLC : début des chaînes des plugins — */
hugerte.addI18n("nl", { "Ajouter un bloc": "Een blok toevoegen", … });
/* — ONLC : fin des chaînes des plugins — */
```

Une seconde exécution remplace cette partie au lieu de l'empiler : les deux commandes peuvent se
relancer dans n'importe quel ordre de répétition. En revanche, `build-langs.js` **efface** le
dossier avant de le réécrire : relancez toujours `build-i18n.js` après lui.

Les codes régionaux (`fr_FR`, `pt_BR`, `sv_SE`…) reçoivent un alias sur leur code court quand
celui-ci est libre : `fr` et `fr_FR` fonctionnent l'un comme l'autre.

### Pourquoi un seul fichier, et non deux

Le cœur ne va chercher son paquet **que si la langue n'est pas déjà déclarée** :

```js
if (!I18n.hasCode(languageCode)) { scriptLoader.add(url); }   // core/init/Render.ts
```

Or un paquet ONLC chargé à la main déclare la langue. Le cœur n'allait donc plus chercher le
sien, et son interface — « Insert », « Bold », « Undo » — restait en anglais sous des formulaires
traduits. On peut s'en sortir en chargeant les deux fichiers à la main, mais c'est une règle de
plus à retenir, qui n'est écrite nulle part dans la documentation de l'éditeur, et qu'on
n'apprend qu'en ouvrant la page. Un fichier complet par langue la supprime.

### L'anglais n'est plus un cas à part

TinyMCE ne livre aucun paquet anglais : son interface **est** écrite en anglais, et son cœur
saute donc le chargement pour ce code. Ici, les plugins sont écrits en français, et c'est
l'anglais qui a besoin d'être traduit. Le cas particulier a été retiré du cœur, et `langs/en.js`
est livré comme les autres — voir le tableau des corrections dans [README.md](README.md).

**Conséquence à connaître** : l'option `language` vaut `en` par défaut. Une configuration qui ne
la précise pas obtient donc une interface **anglaise**. Pour une interface française, écrivez-le :

```js
hugerte.init({ selector: '#contenu', language: 'fr' });
```

## Les plugins ONLC

Les plugins ONLC sont écrits en français : les chaînes du code **sont** les clés de traduction.
Le paquet français ne contient donc rien à traduire — ce sont les clés qui s'affichent.

Quatre langues sont livrées : français, anglais, espagnol, néerlandais.

| Code | Variantes déclarées |
|---|---|
| `fr` | `fr_FR` |
| `en` | `en_GB`, `en_US`, `en_CA`, `en_AU` |
| `es` | `es_ES`, `es_MX`, `es_419` |
| `nl` | `nl_NL`, `nl_BE` |

### Avec les paquets d'origine

Un projet qui charge les paquets **officiels** de TinyMCE — depuis un CDN, ou parce qu'il ne
reprend pas notre dossier `langs/` — trouvera dans `langs/onlc/<code>.js` les chaînes ONLC
seules. Il faut alors charger les deux fichiers, et le paquet du cœur **en premier** :

```html
<script src="/hugerte/hugerte.js"></script>
<script src="https://cdn.exemple/tinymce/langs/es.js"></script>
<script src="/hugerte/langs/onlc/es.js"></script>
<script>
  hugerte.init({ selector: '#contenu', language: 'es' });
</script>
```

L'ordre compte pour la raison expliquée plus haut : le premier chargé déclare la langue, et
l'éditeur n'ira pas chercher le second tout seul.

### Une seule table, et ce qu'elle implique

`addI18n` **fusionne** dans un dictionnaire unique. Nos clés sont **françaises**, celles du cœur
**anglaises**, et quand une clé française s'écrit comme une clé anglaise du cœur, l'une prend la
place de l'autre. C'est arrivé : « Format » désignait chez nous les proportions d'une vidéo, et
le menu « Format » de la barre s'est retrouvé intitulé « Beeldverhouding » en néerlandais. La clé
a été renommée en « Proportions ».

Le générateur tranche désormais à la fabrication plutôt qu'au chargement : **le cœur l'emporte**,
et les collisions sont énumérées à l'écran à chaque exécution. Quatre subsistent — `Emojis`,
`Image...`, `Style`, `Version` — **relues et acceptées** : les deux sens coïncident, et la
traduction convient des deux côtés. Une épreuve fait échouer la suite dès qu'une nouvelle
apparaît, pour qu'elle soit relue elle aussi.

## Ce qui est traduit

1011 chaînes, couvrant les douze plugins : intitulés de champs, titres de dialogues, infobulles
des boutons, noms et descriptions des blocs, phrases d'explication, messages d'état de la
médiathèque et du sélecteur de lieu, catalogue schema.org du référencement et réglages des
diaporamas.

Ne sont pas traduits, volontairement :

* les **contenus produits** — le nom des mois du bloc calendrier, le bouton « Télécharger le
  document » d'un bloc pdf. Ils partent dans la page publiée et s'adressent au **visiteur** : ils
  suivent donc la langue du site, et non celle du rédacteur. Traduire « Télécharger le document »
  avec le paquet de l'éditeur donnerait un bouton néerlandais sur une page française, au seul
  motif que la personne qui l'a posé écrit en néerlandais ;
* les **langues d'un site polyglotte** — `Français`, `English`, `Nederlands` sont écrits dans la
  langue qu'ils désignent, quelle que soit celle de l'interface : c'est ainsi qu'on les reconnaît
  sans les avoir appris ;
* les **catalogues d'icônes** — les mille neuf cents noms de Font Awesome et de Material Design
  sont produits par un générateur à partir des paquets d'origine, et il faudrait les retraduire à
  chaque montée de version des polices ;
* les **valeurs techniques** — `nofollow`, `noopener`, les noms de classes css, les raccourcis
  clavier (`Meta+K`), les dispositions de colonnes (`⅓ + ⅔`) et les extraits de code proposés en
  exemple dans un champ (`color: #c0392b`) ;
* les **marques** — Facebook, LinkedIn, PayPal, OpenStreetMap.

### Vérifier la couverture

Une interface à moitié traduite ne casse rien : elle déçoit, et elle le fait tard, quand un client
néerlandophone ouvre un formulaire et tombe sur trois phrases en français.

```sh
node modules/hugerte/tools/i18n/coverage.js
```

Le relevé donne, module par module, ce qui s'affiche et ce qui manque au tableau. Il est aussi
joué par `yarn test-node` : une chaîne d'interface sans traduction fait échouer la suite.

Ce qu'il cherche : les champs d'un dialogue (`label`, `help`, `placeholder`…), les appels de
traduction, les textes posés dans le dom (`textContent`, `title`, `aria-label`) — et **le html
assemblé à la main**, où la traduction ne se fait pas d'elle-même.

> Ce dernier cas était son angle mort, et il cachait un vrai défaut : la barre de manipulation des
> blocs est écrite en html, ses intitulés ne passaient par aucune traduction, et elle restait donc
> entièrement en français sous une interface néerlandaise. Un relevé qui ne regarde que les
> spécifications de dialogue ne l'aurait jamais dit.

Chaque exemption porte sa raison dans `coverage.js` : une exemption sans motif finit par couvrir
un oubli.

## Ajouter ou corriger une traduction

Pour l'interface du **cœur**, passez par le projet amont : <https://crowdin.com/project/hugerte>,
puis régénérez avec `build-langs.js`.

Pour les **plugins ONLC**, les paquets sont générés à partir d'un seul fichier,
`modules/hugerte/tools/i18n/translations.json`,
qui associe à chaque chaîne française ses traductions, dans l'ordre : anglaise, espagnole,
néerlandaise :

```json
{
  "Ajouter un bloc": [ "Add a block", "Añadir un bloque", "Een blok toevoegen" ]
}
```

Une entrée à laquelle il manque une langue **arrête** le générateur : un paquet incomplet ne se
remarque qu'au moment où quelqu'un ouvre le formulaire concerné, et il est alors trop tard.

Après modification :

```sh
node modules/hugerte/tools/openmoji/build-i18n.js
yarn example-build
```

## Ajouter une langue aux plugins ONLC

Ajoutez une entrée dans le tableau `languages` du générateur — le fichier à produire, les codes
qu'il déclare et la position de la traduction dans le tableau — puis une valeur de plus à
**chaque** ligne de `translations.json`. Le générateur refuse de produire tant qu'il en manque
une, et une épreuve de `yarn test-node` vérifie que les paquets publiés portent tous le même
nombre de chaînes.

Pensez aussi au paquet du **cœur** pour cette langue : `tools/i18n/build-langs.js` en livre
quatre-vingts, et une épreuve vérifie que les quatre langues du projet y figurent. Si le cœur
n'en a pas — c'est le cas de l'anglais —, `build-i18n.js` crée le fichier avec les seules chaînes
ONLC, et il porte alors son propre en-tête.

## Traduire ses propres blocs

Les blocs ajoutés par un projet (`onlc_widgets_custom`, `onlc_shortcodes_custom`) passent par le
même mécanisme : leurs intitulés sont traduits s'ils figurent dans un paquet chargé.

```js
hugerte.addI18n('es', {
  'Horaires d’ouverture': 'Horario de apertura',
  'Du lundi au vendredi': 'De lunes a viernes'
});
```

Appelez-la **après** que le paquet de la langue est chargé, sans quoi vous déclarez la langue
vous-même et l'éditeur n'ira plus chercher le sien — c'est le mécanisme décrit plus haut. Le plus
simple est de le faire depuis `setup` :

```js
hugerte.init({
  selector: '#contenu',
  language: 'es',
  setup: (editor) => {
    editor.on('init', () => hugerte.addI18n('es', { 'Horaires d’ouverture': 'Horario de apertura' }));
  }
});
```
