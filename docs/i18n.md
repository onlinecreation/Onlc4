# Langues de l'interface

Deux jeux de traductions, indépendants l'un de l'autre :

| Jeu | Ce qu'il traduit | Chargement |
|---|---|---|
| `langs/<code>.js` | l'interface du **cœur et du thème** — menus, barres d'outils, boîtes du cœur | à inclure avant `hugerte.init()`, voir ci-dessous |
| `langs/onlc/<code>.js` | les intitulés des **plugins ONLC** | à inclure avant `hugerte.init()` |

> **Les deux vont ensemble, et il faut charger les deux à la main.** Le cœur ne va chercher son
> propre fichier que si la langue demandée n'est **pas déjà déclarée**. Or le paquet ONLC la
> déclare. Charger le paquet ONLC seul laisse donc le cœur en anglais — « Insert », « Bold »,
> « Undo » — sous une interface de plugins traduite. C'est le piège de cette page ; une épreuve
> vérifie que les pages d'exemple chargent bien les deux moitiés.

## Le cœur et le thème

80 paquets sont livrés, produits par `tools/i18n/build-langs.js` à partir des traductions de
TinyMCE 6 (licence MIT, © Tiny Technologies Inc. et les contributeurs). Une seule option suffit :

```js
hugerte.init({ selector: '#contenu', language: 'fr' });
```

Le fichier est chargé tout seul depuis `langs/fr.js` — **tant qu'aucun paquet ne déclare déjà
`fr`**. Dès que le paquet ONLC est présent, il faut charger celui du cœur à la main :

```html
<script src="/hugerte/langs/fr.js"></script>
<script src="/hugerte/langs/onlc/fr.js"></script>
```

Les codes régionaux (`fr_FR`, `pt_BR`, `sv_SE`…) reçoivent un alias sur leur code court quand
celui-ci est libre : `fr` et `fr_FR` fonctionnent l'un comme l'autre.

Pour régénérer les paquets après une montée de version :

```sh
node modules/hugerte/tools/i18n/build-langs.js
```

## Les plugins ONLC

Les plugins ONLC sont écrits en français : les chaînes du code **sont** les clés de traduction.
Sans paquet de langue chargé, leur interface est donc en français, sans configuration.

Quatre paquets sont livrés :

| Fichier | Codes déclarés | Langue |
|---|---|---|
| `langs/onlc/fr.js` | `fr`, `fr_FR` | français (paquet vide : les clés font foi) |
| `langs/onlc/en.js` | `en`, `en_GB`, `en_US`, `en_CA`, `en_AU` | anglais |
| `langs/onlc/es.js` | `es`, `es_ES`, `es_MX`, `es_419` | espagnol |
| `langs/onlc/nl.js` | `nl`, `nl_NL`, `nl_BE` | néerlandais |

### Charger une langue

Le paquet est un simple script à inclure **avant** `hugerte.init()` :

```html
<script src="/hugerte/hugerte.js"></script>
<script src="/hugerte/langs/es.js"></script>
<script src="/hugerte/langs/onlc/es.js"></script>
<script>
  hugerte.init({
    selector: '#contenu',
    language: 'es',
    plugins: 'onlcblocks onlcmedia onlcwidgets onlcicons onlclink onlcspacer'
  });
</script>
```

Ces fichiers appellent `hugerte.addI18n()`, qui **fusionne** dans un dictionnaire unique.

Cette table unique a une conséquence qu'il faut connaître : nos clés sont **françaises**, celles
du cœur sont **anglaises**, et quand une clé française s'écrit comme une clé anglaise du cœur,
elle prend sa place dans toute l'interface. C'est arrivé : « Format » désignait chez nous les
proportions d'une vidéo, et le menu « Format » de la barre s'est retrouvé intitulé
« Beeldverhouding » en néerlandais. La clé a été renommée en « Proportions ».

Quatre collisions subsistent — `Emojis`, `Image...`, `Style`, `Version` — et sont **relues et
acceptées** : les deux sens coïncident, et la traduction convient des deux côtés. Une épreuve
fait échouer la suite dès qu'une nouvelle apparaît, pour qu'elle soit relue elle aussi.

Le nom du fichier est volontairement rangé sous `langs/onlc/` plutôt que `langs/` : un paquet
officiel `langs/es.js` n'est ni remplacé ni écrasé.

## Ce qui est traduit

995 chaînes, couvrant les onze plugins : intitulés de champs, titres de dialogues, infobulles
des boutons, noms et descriptions des blocs, phrases d'explication, messages d'état de la
médiathèque et du sélecteur de lieu, catalogue schema.org du référencement et réglages des
diaporamas.

Ne sont pas traduits, volontairement :

* les **contenus produits** — le nom des mois du bloc calendrier, le bouton « Télécharger le
  document » d'un bloc pdf. Ils partent dans la page publiée et s'adressent au **visiteur** : ils
  suivent donc la langue du site, et non celle du rédacteur. Traduire « Télécharger le document »
  avec le paquet de l'éditeur donnerait un bouton néerlandais sur une page française, au seul
  motif que la personne qui l'a posé écrit en néerlandais ;
* les **langues d'un site polyglotte** — `Français`, `English`, `Nederlands` sont écrits dans la
  langue qu'ils désignent, quelle que soit celle de l'interface : c'est ainsi qu'on les reconnaît
  sans les avoir appris ;
* les **catalogues d'icônes** — les mille neuf cents noms de Font Awesome et de Material Design
  sont produits par un générateur à partir des paquets d'origine, et il faudrait les retraduire à
  chaque montée de version des polices ;
* les **valeurs techniques** — `nofollow`, `noopener`, les noms de classes css, les raccourcis
  clavier (`Meta+K`), les dispositions de colonnes (`⅓ + ⅔`) et les extraits de code proposés en
  exemple dans un champ (`color: #c0392b`) ;
* les **marques** — Facebook, LinkedIn, PayPal, OpenStreetMap.

### Vérifier la couverture

Une interface à moitié traduite ne casse rien : elle déçoit, et elle le fait tard, quand un client
néerlandophone ouvre un formulaire et tombe sur trois phrases en français.

```sh
node modules/hugerte/tools/i18n/coverage.js
```

Le relevé donne, module par module, ce qui s'affiche et ce qui manque au tableau. Il est aussi
joué par `yarn test-node` : une chaîne d'interface sans traduction fait échouer la suite.

Ce qu'il cherche : les champs d'un dialogue (`label`, `help`, `placeholder`…), les appels de
traduction, les textes posés dans le dom (`textContent`, `title`, `aria-label`) — et **le html
assemblé à la main**, où la traduction ne se fait pas d'elle-même.

> Ce dernier cas était son angle mort, et il cachait un vrai défaut : la barre de manipulation des
> blocs est écrite en html, ses intitulés ne passaient par aucune traduction, et elle restait donc
> entièrement en français sous une interface néerlandaise. Un relevé qui ne regarde que les
> spécifications de dialogue ne l'aurait jamais dit.

Chaque exemption porte sa raison dans `coverage.js` : une exemption sans motif finit par couvrir
un oubli.

## Ajouter ou corriger une traduction

Pour l'interface du **cœur**, passez par le projet amont : <https://crowdin.com/project/hugerte>,
puis régénérez avec `build-langs.js`.

Pour les **plugins ONLC**, les paquets sont générés à partir d'un seul fichier,
`modules/hugerte/tools/i18n/translations.json`,
qui associe à chaque chaîne française ses traductions, dans l'ordre : anglaise, espagnole,
néerlandaise :

```json
{
  "Ajouter un bloc": [ "Add a block", "Añadir un bloque", "Een blok toevoegen" ]
}
```

Une entrée à laquelle il manque une langue **arrête** le générateur : un paquet incomplet ne se
remarque qu'au moment où quelqu'un ouvre le formulaire concerné, et il est alors trop tard.

Après modification :

```sh
node modules/hugerte/tools/openmoji/build-i18n.js
yarn example-build
```

## Ajouter une langue aux plugins ONLC

Ajoutez une entrée dans le tableau `languages` du générateur — le fichier à produire, les codes
qu'il déclare et la position de la traduction dans le tableau — puis une valeur de plus à
**chaque** ligne de `translations.json`. Le générateur refuse de produire tant qu'il en manque
une, et une épreuve de `yarn test-node` vérifie que les paquets publiés portent tous le même
nombre de chaînes.

Pensez aussi au paquet du **cœur** pour cette langue : `tools/i18n/build-langs.js` en livre
quatre-vingts, et une épreuve vérifie que les quatre langues du projet y figurent.

## Traduire ses propres blocs

Les blocs ajoutés par un projet (`onlc_widgets_custom`, `onlc_shortcodes_custom`) passent par le
même mécanisme : leurs intitulés sont traduits s'ils figurent dans un paquet chargé.

```js
hugerte.addI18n('es', {
  'Horaires d’ouverture': 'Horario de apertura',
  'Du lundi au vendredi': 'De lunes a viernes'
});
```
